# AGENTS.md

Guidance for AI coding agents, and for humans, working in this repository.

## Project

Actio is a self-hostable, local-first AI platform. It combines a chat assistant, an OpenAI/Anthropic-compatible developer gateway, and Claude-inspired usage limits. Design decisions live in [`docs/adr/`](docs/adr/).

## Ground rules

- **Small steps.**
  - Make one focused, tested change at a time. There is no size limit: a step is done when it works end to end, with its tests.
  - Explain what changed, why, and how to verify it.
- **Humans commit.** Agents never commit, push, or create remote resources. The maintainer reviews and commits every change.
- **No secrets in the repo.**
  - Never commit `.env` files, keys or tokens.
  - Tests must never read `.env`; they use fakes and generated test config.
  - Commit hooks scan for secrets (gitleaks) and for private names listed in `~/.config/actio/denylist.txt`, which stays outside the repo.
- **Never bypass the checks.** Don't use `git commit --no-verify`; fix what the hook reports.
- **Written from scratch.**
  - Don't paste code from other projects.
  - Third-party code enters only as declared dependencies with compatible licenses: MIT, BSD, Apache-2.0 and similar permissive ones, or the LGPL for a library used unmodified ([ADR 0008](docs/adr/0008-postgres-through-sqlalchemy-and-psycopg.md)). No GPL or AGPL code.
  - Check a new dependency's license from its own metadata before adding it. If it reaches a container image under anything but a permissive license, list it in `THIRD_PARTY_NOTICES.md`.
- **Fictional data only.** Demo content, such as the "Velora Cycles" knowledge base, is fictional.

## Layout (planned)

| Path | Purpose |
|---|---|
| `apps/api` | FastAPI modular monolith (`python -m actio --role api\|migrate\|worker\|all`, where `all` is the API with the worker inside it, as `make dev` runs it). `api/` is the HTTP interface, and `worker.py` the process that runs background jobs, with the list of every job it runs; `chat/` holds conversations, their tree of messages and the turns in which a model answers, which run apart from the requests that start them, the count of who reads along with them, and the titles a model writes for them (`titles.py`); `catalog.py` holds the models on offer, and the gates in front of their servers; `identity/` holds accounts and sessions; `usage/` holds the prices and plans, the usage ledger with its notes of what the counters haven't been told of yet, the limits on what answers may cost, and the job that tells the counters what they missed (`missed.py`); `core/` holds settings, ids, the database, the queue of background jobs (`jobs.py`), the file by which the worker says that it works and its health check (`alive.py`), the rate limiter, what a process holds open while it runs, with the usage limits' engine (`resources.py`), the listener for the signal that stops the process, and the rule for text that can be stored (`text.py`); `migrations/` holds the schema's history |
| `apps/web` | Next.js web app: the chat. `app/` holds the pages, which only place components, the layout around them, with the one script the app writes into the page, at the start of its body, and the icon (`icon.svg`, and `favicon.ico` for whatever asks for the default address); `components/` the interface: the conversation on the page (`components/chat`), the list of conversations beside it (`components/sidebar`), the forms for signing up, logging in and the account (`components/account`), and the usage limits: the meter under the list and what is said at a limit (`components/usage`); `lib/` what it is built on: the calls to the API (`lib/api`, with types generated from the API's description), how a turn is requested and read along with, how an answer's markdown is read, how its code is coloured, in a worker, and how the list of conversations is kept (`lib/chat`), whose session the page has (`lib/session.ts`), what the page's frame and that script agree on (`lib/frame.ts`), what was used of the usage limits and whether one is reached (`lib/usage.ts`), times in words (`lib/time.ts`), ids and the address bar; `tests/` the fake API and the recorded answers the component tests run on; `e2e/` the end-to-end tests, which Playwright runs against the stack of `make e2e` |
| `packages/quota` | Usage-limits engine: Lua scripts plus a Python reference model |
| `packages/llm` | Model clients: the neutral chat format, the Ollama adapter and the OpenAI-compatible adapter (`actio-llm`), and a guess at a text's tokens for when no provider has counted them; the router comes later |
| `packages/fakellm` | Deterministic fake LLM server for tests, scripted by directives in the prompt (`[[think: ...]]`, `[[call: ...]]`, `[[fail: 503]]`, `[[pace: 0.1]]`, `[[say: ...]]`). It serves two models: `fake-chat` echoes the question, and `fake-quiet` says nothing but what `[[say: ...]]` tells it to. Its `Dockerfile` builds the image the end-to-end stack runs |
| `config/` | What an installation changes without touching code. Today `models.toml`, the models on offer ([ADR 0013](docs/adr/0013-the-models-on-offer-are-a-file.md)) and the one that names conversations ([ADR 0025](docs/adr/0025-titles-written-by-a-model.md)), which the API and the worker read, and `plans.toml`, what they cost and how much each kind of account may use ([ADR 0020](docs/adr/0020-usage-limits-on-turns.md)); assistant profiles and the demo knowledge base come later. TOML, which Python reads without a dependency |
| `compose.yaml` | The production-shaped stack behind `make up`: Caddy, web, API, the worker, Postgres, Valkey, which keeps nothing on disk, and the `migrate` job that runs before the API and the worker. The API and the worker read the models file from one mount, and reach the models' servers through the `models` network, the worker's one way out |
| `compose.dev.yaml` | The overlay behind `make dev`: Caddy routes to the native processes; data ports open on 127.0.0.1 |
| `compose.e2e.yaml` | The overlay behind `make e2e`: the same stack, its worker included, with the fake model as one more container on the `models` network, made internal there, which the API and the worker wait for, and the models and plans files in `deploy/e2e/config/`, which the API and the worker read, that offer it three times, once for nothing and once, its quiet model, to name conversations, and give accounts a usage limit within reach ([ADR 0017](docs/adr/0017-end-to-end-tests-on-the-real-stack.md)) |
| `deploy/caddy/` | The proxy: its config, one entry point routing `/api/*` and `/v1/*` to the API, the rest to the web app, refusing a body over 2 MB on the API's routes, and compressing what the API answers as JSON, with gzip; and the `Dockerfile` that builds the config into the pinned Caddy image, and checks it. A change to the config takes effect when `make up` or `make dev` is run again |
| `deploy/tests/` | Policy tests for the containers: published ports, pinned images, networks, hardening, health checks, the waits at a stop, and the one restart policy, the worker's |
| `docs/` | The documentation site's pages (built by Zensical from `zensical.toml`), including the ADRs in `docs/adr/` |
| `scripts/` | Developer scripts. `read_only_git.py` is the check that keeps the reviewing agent's shell to git commands that only read, and `tests/` holds its tests |
| `.claude/` | The two agents that Claude Code's main session hands work to (`agents/`): a coder, which builds a step's first version, and a reviewer. How they work with the main session is in `CLAUDE.md` |
| `conftest.py` | Test fixtures shared by every suite: a throwaway Postgres and Valkey, from the images pinned in `compose.yaml` |

## Commands

| Command | What it does |
|---|---|
| `make help` | List available targets |
| `make doctor` | Check that required tools are installed. Prints install hints; installs nothing |
| `make bootstrap` | Set up a fresh clone: `doctor`, `install`, a `.env` with random passwords, then pull the images |
| `make install` | Install the Python and JavaScript workspaces with their dev tools, plus the git hooks |
| `make up` | Build and run the whole stack in containers, shaped like production, at http://localhost:8080 |
| `make dev` | Run the stack at http://localhost:8080 with the API and web app native, with hot reload. The worker runs inside the API's process (`--role all`), and reloads with it |
| `make smoke` | Check a running stack through Caddy: the web page, and that the API is healthy, ready (database migrated, Valkey answering, and under `make dev` the worker inside the API working), serves its docs, starts a guest session, lists its models and says what a guest may use |
| `make migration name="..."` | Write a new database migration from the table models, as a numbered draft to read and edit |
| `make openapi` | After a change to a route or a schema: record the API's description again (`apps/api/openapi.json`), and generate the web app's types from it (`apps/web/lib/api/schema.d.ts`). Review the difference |
| `make docs` | Preview the documentation site at http://localhost:8001, reloading on edits |
| `make down` | Stop all containers. Their data stays in Docker volumes |
| `make check` | Run what CI's main job runs: every static check on all files, the tests, then the builds (web app and docs site). The end-to-end tests are apart: `make e2e` |
| `make test-live` | Run the model-client tests against a real Ollama server (0.40 or newer, with `granite4:micro` pulled). Not part of `make check` |
| `make e2e` | Run the end-to-end tests: build and start a stack of its own (port 8090, its own data, a fake model), drive it in a real browser with Playwright, and remove it. Needs Docker; about a minute. Not part of `make check`: CI runs it as its own job. `make e2e args="--headed --workers 1"` passes arguments to Playwright, here to show the browser, one test at a time (the first such run downloads the whole of Chromium, about 200 MB). `ACTIO_E2E_KEEP=1` leaves the stack running, and `make e2e args=down` stops it |
| `make fmt` | Format code and apply safe lint fixes |

`make lint`, `make test` and `make build` run the parts of `make check` on their own. The static checks are defined once, in `.pre-commit-config.yaml`, and run at every commit, in `make check` and in CI. Processes can also run alone: `uv run actio --role all --reload`, the API with the worker inside it, as `make dev` runs it, or `uv run actio --role api --reload` without the worker, `uv run actio --role worker`, which runs the background jobs alone, `pnpm --dir apps/web dev`, or the fake LLM server with `uv run fakellm`. `uv run actio-llm chat <model> "<prompt>"` talks to a local model through the Ollama adapter. The web app is tested at two levels: its components in a simulated browser, against a fake API (`make test`), and the whole stack in a real browser, with a fake model (`make e2e`). A change to the chat should pass both, and be looked at once at http://localhost:8080.

`make up` needs only Docker; it builds the images from `apps/api/Dockerfile`, which the migration job and the worker run too, `apps/web/Dockerfile` and `deploy/caddy/Dockerfile`, the proxy with its config. `make dev` stops the worker's container, and builds the proxy's image too, so a change to `deploy/caddy/Caddyfile` takes effect when either is run again. `make dev` needs Docker Desktop: its containers reach the natively running API and web app through `host.docker.internal`. Changes to the containers must keep `deploy/tests/` passing; if a rule must change, change the test on purpose and record why in an ADR. `.env` holds the local passwords. It is created once from `.env.example`, git-ignored, and never read by tests. Postgres keeps the password it first started with, so if you recreate `.env`, also wipe the local data with `docker compose down --volumes`.

## Conventions

- **Python:**
  - 3.13, managed with `uv`;
  - add dependencies with `uv add`, never `pip`; run tools through `uv run` or `make`;
  - workspace packages are named `actio-<name>` and imported as `actio_<name>`, such as `actio-fakellm`;
  - formatted and linted with `ruff`;
  - `mypy --strict` on core packages;
  - tests with `pytest`; property and state-machine tests with Hypothesis (`HYPOTHESIS_PROFILE=dev|ci|nightly`);
  - `make test` fails below 90% coverage of `packages/quota`, and needs Docker running: the quota and API tests start throwaway Valkey and Postgres containers;
  - a change to a table model needs a migration in the same commit (`make migration name="..."`): a test fails when the models and the migrations disagree. Never edit a migration that is already on `main`; write the next one;
  - the queue of background jobs is Procrastinate's, pinned to an exact version: migration 0009 builds its tables from the package's own SQL files, up to that version ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md)). An upgrade is a new pin and a new migration that applies the package's files after the version the last one names. A test that compares the queue with the package's `schema.sql` fails until both are there;
  - `apps/api/src/actio/core` imports nothing else from `actio`;
  - a file in `config/` is read through `actio.core.config_file`, which says a mistake in it in one line. The API's command line reads each such file before starting, so a mistake stops it there;
  - in the API's tests a credit is a token and the usage limits are out of reach. A test that wants to reach one asks for plans, `plans_with(guest=(1_000, 10_000))`, and a `ScriptedModel`'s last event says what a turn used. The limit on answers at once is out of reach too, unless asked for: `plans_with(answers_at_once=1)`. A test of the gate in front of a model's server offers its models through `lineup`, each with a script of its own, behind a `Gate` it chooses;
  - a test of an answer that is still being written starts the request as a task, waits for `model.waiting` (a `ScriptedModel` held at an `asyncio.Event` of its script), acts, and looks at the response afterwards: in process a response comes back whole. Only what takes a connection that closes goes in `test_turns_live.py`. A request that could wait for ever on a broken app gets a time limit, so the test fails instead of hanging;
  - a test of background jobs defers them through its database session, and runs them with `work_through(jobs.Job(...))`: a worker in the test's process that returns once nothing is left. One that needs a worker that waits starts `jobs.work(..., on_signals=False)` as a task and cancels it, which stops it as the process's signal does. A test of the signals themselves sends real ones to its own process, with a handler of its own in place first, and puts back what it found, pass or fail. The real process, and its signals, are tested in a subprocess (`test_worker.py`). A test of the worker's beat makes it short: `monkeypatch.setattr(alive, "BEAT_S", 0.05)`. A test of the worker inside the API opens the app with `open_app(settings, with_worker=True)`, which runs the jobs of `worker.listed`: the test replaces that list with jobs of its own, and defers before the app starts, since a job committed in the instant a worker starts can wait five seconds for its next look (`test_all_role.py`). A test of the look after the queue writes what a dead worker leaves through `queue_books`, from a job of its own that runs before the look: a worker that starts takes the dead ones off the list itself. A job put back after an error is dated by its worker's clock, and a worker that waits looks for it only every five seconds: so a test of one gives its listing waits of a minute or more, which never end by themselves while it runs (the title job's tests use its own, half a minute at the least), reads in how long the job is due (`queue_books.due()`, by the test process's own clock, which dated it), ends the wait through the database (`queue_books.wait_is_over()`), and runs a worker again. None sleeps through a wait;
  - change the Lua in `packages/quota` only together with the Python reference model (`oracle.py`): the differential test requires both to behave identically;
  - the same holds for the rate limiter's script, `apps/api/src/actio/core/rate_limit.lua`, and the plain token buckets in `apps/api/tests/test_rate_limit.py`;
  - new HTTP client code uses `httpx2`, the maintained continuation of httpx ([ADR 0007](docs/adr/0007-local-models-through-ollamas-native-api.md)). The older test fixtures that call an app in-process still use httpx;
  - the Ollama adapter's tests replay recorded exchanges (`packages/llm/tests/fixtures/`), and fail if the request it sends changes. After changing what it sends, run `ACTIO_RECORD_OLLAMA=1 make test-live` to record them again from a real server, and review the diff;
  - what a turn streams is recorded too, in `apps/api/tests/fixtures/turns/`, and the web app's tests read those files with the real `ai` package ([ADR 0014](docs/adr/0014-turns-streamed-in-the-ai-sdks-format.md)). After changing the stream on purpose, run `ACTIO_RECORD_TURNS=1 uv run pytest apps/api/tests/test_turn_fixtures.py`, review the diff, then `pnpm --dir apps/web run test`. The refusal of a turn at a usage limit is recorded beside them (`limit_reached.json`), and changes the same way. So do a stream that ends because its turn was stopped (`stopped.sse`), one with the line that keeps a silent connection open (`keep_alive.sse`), and what someone who reads along is sent when the turn's stream is gone (`lost.sse`).
- **TypeScript:**
  - `pnpm` 12; pnpm also installs the Node.js version pinned in the root `package.json` (26 LTS);
  - add dependencies with `pnpm --dir apps/web add`, never `npm`. pnpm refuses a version published less than a day ago: take the newest one that is older;
  - the `ai` package is pinned to an exact version: the API writes the stream it reads ([ADR 0014](docs/adr/0014-turns-streamed-in-the-ai-sdks-format.md)), so an upgrade is a change to check, not to drift into. `@ai-sdk/react` is pinned with it: each of its versions depends on exactly one version of `ai`, so the two move together;
  - only the browser calls the API, through `lib/api/client.ts`. No server component, route handler or server action does: the session is the browser's cookie, and the API counts requests by the client's address ([ADR 0015](docs/adr/0015-the-web-chat-calls-the-api-from-the-browser.md));
  - `lib/api/schema.d.ts` is generated from `apps/api/openapi.json`. Never edit it: run `make openapi`. A test fails when it is out of date;
  - the server is the truth about a conversation. The chat library's state is what is shown while an answer streams; when a turn ends any other way than well, the page reads the conversation again instead of working out what happened (`resync` in `components/chat/chat.tsx`);
  - a stored conversation comes onto the page newest first: its newest 20 messages at once, and the older ones behind them, 20 at a step ([ADR 0015](docs/adr/0015-the-web-chat-calls-the-api-from-the-browser.md), revision "a long conversation opens newest first"). Each step is drawn out of sight, as a transition begun from an effect once the one before is committed, in an element of its own that stays its messages' parent and is `hidden` until it is shown. It is shown, a step at a time, in a task of its own, and only once `useFollow` says that the reader is still (`untilStill`): in Firefox and WebKit a change above the reader overrides a scroll under way. That task asks where the reader stands (`standing`), shows the step with `flushSync`, and tells the hook right after (`addedAbove`), which keeps the reader's place by how far the first thing shown moved, and moves the hook's own note of where they were: without the note, a scroll up told of after messages were shown above is taken for one down, and the reader is pulled back to the end. Only the drawing and the showing start later in the list: everything else reads all of `messages`, and which message is `writing` is counted in the whole list. `Message` is memoized, so nothing that is new at every render may be passed to it. Without these, `components/chat/newest-first.test.tsx`, `components/chat/follow.test.tsx` and `e2e/newest-first.spec.ts` fail;
  - only Stop ends an answer ([ADR 0022](docs/adr/0022-turns-that-run-apart-from-their-request.md)). The page stops reading, then stops the turn the server says is running (`resync({ stop: true })`). Nothing else may ask for that: the chat library ends its reading whenever its component leaves the page, which is no stop. A component test fails if the page asks to stop a turn because a conversation was left or deleted;
  - an answer that the conversation says is being written, and that the page isn't reading, is read along with ([ADR 0022](docs/adr/0022-turns-that-run-apart-from-their-request.md), revision of 2026-11-17): the page joins that turn's stream by its id, through the library's `resumeStream`, never `useChat({ resume: true })`, which asks by the conversation alone whenever its component appears. One try for each turn while its conversation is on the page. When the join can't be made, or its stream ends in an error, the page reads the conversation, and if the turn still runs it looks every second and a half until it is over (`elsewhere`): a stream that is gone stays gone, so a second try would go in a circle. A join that the page gave up itself is no try: React's StrictMode, as in `make dev`, runs the effect that joins twice, and a component test opens the app that way (`open(path, { strict: true })`). A join says nothing of its own failure. The notice of the page's own reading that broke off goes once the page reads along again (`brokeOff`); no other notice does;
  - the page moves between conversations through `lib/location.ts` (the browser's history), not with `next/link` or the router: a navigation would end an answer that is streaming. The same goes for every other place in the app, such as `/login`: a link to one is an `InAppLink` (`components/in-app-link.tsx`), and a new place is a case in `placeIn` plus a page file that renders `ChatApp`;
  - whose session the page has comes from `lib/session.ts`, and changes only with what the API answered ([ADR 0019](docs/adr/0019-accounts-in-the-one-screen.md)). Whatever is read from the API for whoever has the session is held under `session.holder`, as the list of conversations, the models and the usage are: never under a fixed name or the account's id. Then it is dropped when the session ends, and the same account logging in again reads it anew;
  - what arrives with the session fills a place that was already there: nothing on the page before the session moves when it arrives ([ADR 0015](docs/adr/0015-the-web-chat-calls-the-api-from-the-browser.md), revision of 2026-11-21). The header's buttons are there from the first paint, disabled and unseen until then, and an empty place of the list's width stands where the list will be while nobody has a session. Nothing rendered before the session may depend on what only the browser knows: the remembered switch, which is read at the browser's first render, where React doesn't repair an attribute that differs from the HTML it takes over; or the window's width, which is read right after, and would change the page in front of the reader. CSS decides, with the mark that the one script the app writes into the page puts on `<html>` before the first paint when the list was put away (`data-list-away`, the variant `list-away:` in `app/globals.css`), and that the page keeps in step with the switch. What the script and the page agree on is in `lib/frame.ts`. That script, a constant, is the app's one use of `dangerouslySetInnerHTML`. It is the first thing the layout writes into the body, before the page's content, and not in the head: there, after the stylesheet, it held the parser until the stylesheet was in, and meanwhile Chromium asked for the page's scripts one at a time (ADR 0015, revision of 2026-11-22). A component test hydrates the server's HTML as three visitors and fails at any mismatch (`components/chat/frame.test.tsx`), and an end-to-end test fails when the frame moves as the session arrives (`e2e/frame.spec.ts`). With the script back in the head, `app/layout.test.tsx` and `e2e/first-load.spec.ts` fail;
  - what answers cost is the server's to count ([ADR 0021](docs/adr/0021-usage-limits-in-the-page.md)). The page reads the counts through `lib/usage.ts` and reads them again after a turn (`refresh`): it never adds up credits, and never works out from the counts whether a question fits. That a limit is reached it learns from a refusal: what refuses a turn is shown to `usage.refused` first, which holds a usage limit for the session until the wait is over. Anything else is that question's own problem;
  - a time is said through `lib/time.ts`: by the reader's clock, in the page's words (`atTime`), or as the time left (`timeLeft`). What counts down is a `role="timer"` in a `Notice` that is `changing`, never inside a `role="status"`: a screen reader would say it every second;
  - a form says what is wrong under the box it is about (`Field` in `components/account/form.tsx`), in the API's words where the API said it, and puts the keyboard on that box. The browser's own validation is off (`noValidate`). A limit a form holds people to is the API's, kept in `lib/account.ts` and checked against the API's description by `tests/contract/limits.test.ts`;
  - the list of conversations is the server's too ([ADR 0018](docs/adr/0018-the-list-of-conversations-is-the-servers.md)). Everything reads and changes it through `lib/chat/list.ts`. After something that changes the list, read it again (`refresh`): never insert, move or sort rows on the page. A rename or a delete shows once the server has done it, not before. While the list's first page says that a conversation's title is on its way (`title_pending`), the list's own hook reads it again every second, until it no longer says so: the page follows that member, and never works out from titles or times whether a title is coming. The first page alone decides, since a look reads the first page alone: one further down would be looked for without end ([ADR 0025](docs/adr/0025-titles-written-by-a-model.md), revision of 2026-11-20);
  - what the interface does is a link or a button with a name. After an action the keyboard's focus is put somewhere on purpose, and the action's test says where;
  - components are written here. Third-party interface code comes in as a declared dependency, never as source copied in, which rules out shadcn/ui-style generators ([ADR 0015](docs/adr/0015-the-web-chat-calls-the-api-from-the-browser.md));
  - a model's words reach the page through one component, `components/chat/markdown.tsx`, and no other way: never through `dangerouslySetInnerHTML`. That file decides what an answer may do: no HTML, no fetched pictures, a link only after its address was shown ([ADR 0016](docs/adr/0016-answers-shown-as-markdown.md)). A rule loosened there fails a test in `markdown.test.tsx`; change one only on purpose, with the ADR;
  - nothing else imports `streamdown` or its plugins, but for the types the code plugin written here takes from it (below). That component stays a piece apart from the page, which keeps about 240 kB out of the page's first load: `message.tsx` fetches it once a page, and an answer is shown as markdown from its first render once it is there, never as written first and swapped. `ChatApp` asks for it ahead (`fetchRenderer`), once the page knows whose session it has, the list of conversations has been read or couldn't be, and the frame that shows that has been painted (`afterPaint` in `lib/after-paint.ts`): run as it arrives, its code held back the list's rows ([ADR 0016](docs/adr/0016-answers-shown-as-markdown.md), revision of 2026-11-22). Without that wait, `components/chat/renderer.test.tsx` and `e2e/renderer.spec.ts` fail. Whatever needs it before that asks for it at once, with no frame to wait for: the first letter of a question written into the box (`components/chat/chat.tsx`), since nothing keeps one from being asked while the list is still read, and through `useRenderer` an answer on the page, before its first word, and a stored conversation. While it is on its way, none of an answer's words is on the page, whether the answer is arriving or complete: the answer says "Waiting for the model…" in their place, and a stored conversation isn't shown. The page waits for it once, `RENDERER_WAIT_MS` at the most, counted by the clock from the first moment something on it had words to show: one wait, kept in `message.tsx` beside the renderer's state, which the answers and the stored conversation share (`useWaitsForRenderer`). After it, what waited and whatever comes later is shown as written until the renderer is here, and at once when it can't be had (revisions of 2026-11-21 and "an answer that arrives waits for the renderer too"). Without that, `components/chat/renderer.test.tsx` and `e2e/renderer.spec.ts` fail. A component test that says when a frame comes holds the frames (`holdFrames` in `tests/frames.ts`). A piece of an answer's text whose markdown throws while it is drawn, as when a part the library fetches by itself can't be had, is shown as written in its place by an error boundary around the renderer in `message.tsx` (`AsWrittenOnError`), one for each piece, the reasoning's too: it isn't tried again while the answer arrives, and is tried once more when the answer is complete (revision "an answer that can't be drawn is shown as written"). Without it, `components/chat/as-written.test.tsx` and `e2e/as-written.spec.ts` fail. - **Architecture boundaries,** enforced by import-linter at every commit and in CI. The rules are in `pyproject.toml`, under `[tool.importlinter]`:
  - `packages/*` never import the application, or each other;
  - inside `actio`, imports only point down the layers: `cli`, `app`, then `api` and `worker` side by side, `tables`, `chat`, then `catalog`, `identity` and `usage` side by side, `core`. So `core` imports nothing else from `actio`, `api` and `worker` don't import each other, and `catalog`, `identity` and `usage` don't import each other;
  - only `actio.api` imports the web framework. `core`, the domain modules, `chat`, `catalog`, `identity` and `usage`, and `worker` never do;
  - only `actio.core.jobs` imports Procrastinate. Everything else defers a job with `jobs.defer` and lists its handler in `actio.worker`, so the queue can be replaced by rewriting one module ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md));
  - a new module directly under `actio` must be given a layer in that list, or the check fails. A new domain module goes among the domain modules, above the ones whose tables it points at, and joins the rule against importing the web framework;
  - a table that points at another module's table names its class, such as `ForeignKey(User.id)`, never the text `"users.id"`. Then loading one table module loads what it needs, and a process that loads only that one still works. A test loads each alone.
- **API conventions:**
  - routes live in `actio.api`; rules and tables live in a domain module below it, which never commits: the route decides when the unit of work is done;
  - a request's body is a `Body` (`actio.api.body`), never a bare `BaseModel`: a test fails otherwise. A body is JSON, which can spell two kinds of character that can't be stored: U+0000, and half of a surrogate pair, as an emoji cut in two leaves it. `Body` puts U+FFFD in the place of each, in every string and every member's name down to sixteen levels, far below any request, before anything reads the request (`actio.core.text.storable`, [ADR 0008](docs/adr/0008-postgres-through-sqlalchemy-and-psycopg.md), revision of 2026-11-20). What a model writes gets the same where it comes in: an answer in `Answer` (`actio.chat.answering`), before a reader is shown it. Text from a new source, such as a tool's result or a file, goes through `storable` where it comes in too, not where it is stored. The refusal of a body (422) says where it is wrong and never repeats what was sent, and has to stay so: a string below those sixteen levels wasn't looked at. An address for a new account that holds the mark is refused (`SignUp`): the rules for an address would take it;
  - errors are RFC 9457 problem documents: raise `Problem(status, detail)`. `detail` is shown to people as it is, so write it for them;
  - a route lists the errors it answers in its `responses`, with a description each. The `Problem` schema is filled in for them. A route that takes `CurrentPrincipal` passes `NO_SESSION`, or its router does: a test fails otherwise;
  - the API's description is recorded in `apps/api/openapi.json`, and the web app's types are generated from it. After changing a route or a schema, run `make openapi` and review the difference: tests on both sides fail until then;
  - reading a conversation whole takes several queries. Call `conversations.hold_still` first, so a turn that ends meanwhile isn't seen half ([ADR 0014](docs/adr/0014-turns-streamed-in-the-ai-sdks-format.md), revision of 2026-11-13);
  - nothing below `actio.api` reads the clock. Time comes in as `now`, from the `Now` dependency, so tests can move it. A route that lasts, such as a streamed answer, takes `Clock` and reads it again at the end. Ids the server makes in a route come from `NewId`, so a test knows them beforehand;
  - a job that follows a change is deferred in that change's transaction, by its name: `await jobs.defer(db, "name", ...)` (`actio.core.jobs`), which never commits. It is there once the transaction commits, and never if it is rolled back. A job the database refuses raises `jobs.DeferError`, one of SQLAlchemy's errors, as any failed statement of the session does. Its arguments are JSON, and Procrastinate writes them in the log: ids, not what people wrote. Its handler is listed in `actio.worker`, with what it needs bound in; a job whose name no worker lists ends as `failed` ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md)). The worker is a top layer like the API: it reads the clock, and passes it on as `now`;
  - a job's handler is safe to repeat: a job may run more than once, from its start each time ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md), revision of 2026-11-20). A stop that cuts it off at the end of its grace puts it back into the queue, and so does the worker's look after the queue when the worker that had it died. The scheduled jobs each take a batch of what is left to do, which a second run doesn't find again; the title job looks first whether its conversation still wants one. With more than one worker, a job could also run twice at once, when a worker that was only late is taken for dead: so a handler takes what it works on in a way that a second run beside it doesn't, as the batches' `SKIP LOCKED` does;
  - a job that fails is not run again, unless its listing names the error as worth another try: `jobs.Job(name, run, again=jobs.Again(errors=(SomeError,), waits=(…)))`, the first wait before the first time it is run again, and the last serving any time after it ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md), revision "a job is run again after an error its listing names"). List an error of the handler's own, and only one that may be gone at a later try: a database that refused a statement, or a mistake in the code, comes back each time. The count is one, whatever the reason, after a stop, a worker that died or such an error: `jobs.RUNS_AGAIN` times in all, kept in the job's `attempts`, so a job that was cut off once has a try fewer after an error. The handler says in the log what went wrong, in one line, before it raises: the queue's line for a job put back carries no trace, and names no error. It raises the error without its cause (`from None`), and its text holds kinds and ids, never what people wrote: the last try fails the job, and its trace, a cause's text included, is in the log;
  - every ten minutes the worker looks after its own queue (`look-after-the-queue`, `worker.LOOK_AFTER_QUEUE`): it runs again the jobs a dead worker left `doing`, or ends those at the limit as `failed` with a warning, takes dead workers off Procrastinate's list, and deletes failed, aborted and cancelled jobs once they are `worker.KEPT_FOR` old. It reaches the queue through `jobs.Queue`, which a job listed with `with_queue=True` is given: nothing of Procrastinate leaves `actio.core.jobs`. The queue's books are Procrastinate's, its heartbeats and the times its jobs ended, written by the database's clock, so that job takes no `now`: the one job that doesn't. A worker that is stopping no longer says that it is alive, so `jobs.BEATS_EVERY_S` plus `jobs.SHUTDOWN_GRACE_S` stays under `jobs.WORKER_DEAD_AFTER_S`, or a test fails;
  - a conversation says who named it (`Conversation.title_by`): `question`, while its title is its first question's first line, which a model may replace; `model`; or `person`, which nothing writes over ([ADR 0025](docs/adr/0025-titles-written-by-a-model.md)). A rename makes it `person` (`conversations.rename`), and only the title job makes it `model`. That job, `write-title` (`titles.WRITE_TITLE`), is deferred in `turns.finish`, once for a conversation, by its first turn that completes, when the models file names a model for titles: the route passes `catalog.titles is not None` down, since `actio.chat.turns` doesn't know the catalog. It is deferred inside a savepoint, so that one the queue refuses never keeps the turn from being recorded. Its handler, `titles.write`, asks nothing for a conversation that is gone or no longer `question`, and asks again under the row's lock before it writes: so a person's title is never written over, and the job is safe to repeat and to run beside itself. It holds no database connection while the model writes, lets a cancellation out as it came, keeps the question and the title out of the log, and costs the account nothing. A model that isn't ready is not asked, as a turn doesn't ask one. A title the model couldn't give for now, its server unreachable, away, failing or refusing for now, its answer broken off, or the 30 seconds over, raises `titles.NotWrittenError`, which the job's listing names: it is asked for again after 30 seconds, 2 minutes and 10 minutes (`titles.ASKED_AGAIN_AFTER`), and after the fourth try the job fails and the first line stays ([ADR 0025](docs/adr/0025-titles-written-by-a-model.md), revision "a title its model couldn't give for now is asked for again"). One it won't give, a model missing from its server, a request the provider refused, or nothing to make a title of, ends the job well. A long title, a first line's or a model's, is cut by one rule, `titles.cut`;
  - a statement that fails is said without its values: the engine is made with `hide_parameters=True` (`actio.core.database`, [ADR 0008](docs/adr/0008-postgres-through-sqlalchemy-and-psycopg.md), revision of 2026-11-20). The values are what people wrote, a question, an answer, a title, and an error's text ends up in the log, with its trace. For the same reason a log line about a model's error names the error's kind, never its text, which may quote the question;
  - the worker has the models on offer: `worker.listed` takes the catalog. `--role worker` reads the models file before it starts, as the API does, so that a mistake in it is one line and status 2, and builds a catalog of its own; `--role all` gives its worker the app's own, so that a title waits at the same gate as the answers. The worker doesn't read the plans file. Its container mounts `./config` as the API's does, and finds Ollama by the same variable and host, through the `models` network, its one way out of the stack: a test in `deploy/tests/` holds the two alike;
  - a job that works through rows in batches takes its batch by a statement of its own, `SELECT … LIMIT … FOR UPDATE SKIP LOCKED`, and changes no other rows of that table after it: see `sessions.delete_expired`, which deletes them in the next statement, `turns.give_up_on_stale_everywhere`, which gives up on them one by one, and leaves those whose conversation another transaction holds, and `missed.count_missed`, which holds only its own table's rows of a join (`with_for_update(of=…)`). Never the batch as a subquery of the statement that changes the rows: a plan that reads the subquery again for each row goes past the limit ([ADR 0011](docs/adr/0011-rate-limits-as-token-buckets-in-valkey.md), revision of 2026-11-19). One batch a run, and what is left goes in the next;
  - the worker hears SIGTERM and SIGINT itself, in `jobs.work`, from before it connects, and stops Procrastinate's worker by cancelling it: Procrastinate's own handling of the signals stays off. The first signal counts, later ones change nothing, and told at any time the process ends with status 0. A worker that Procrastinate stopped by itself, as it does when the database restarts, starts again (`STARTS_AGAIN_AFTER_S`);
  - the worker's container ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md), revision of 2026-11-19) has no port: its health is a file it touches every `alive.BEAT_S` while it works, named by `ACTIO_ALIVE_FILE`, and its health check, `python -m actio.core.alive`, finds it fresh for `alive.STALE_AFTER_S`. That module imports only the standard library, which a test holds: Docker starts it every few seconds. Its `main` is a process of its own and reads the clock itself; `fresh` takes the time as `now`, like everything else below `actio.api`. Each time the worker has connected, it checks that the database is at its code's migration before it takes a job, and ends with one line when it isn't. It is the only container with a restart policy, `on-failure`: it ends when it can't go on, and Docker starts it again, but not after it was told to stop. After Docker itself was restarted it stays down with the rest of the stack, because Docker stops it first and it ends well: don't make it end with another status when it is told to stop. Told to stop, it gives the job in hand `jobs.SHUTDOWN_GRACE_S`, and its `stop_grace_period` in `compose.yaml` has to be longer, or a test in `deploy/tests/` fails;
  - `--role all` is the API with the worker inside its process, as `make dev` runs it ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md), revision of 2026-11-19). uvicorn calls `create_app_with_worker`, and the app's lifespan runs `actio.worker.run_inside` in a task, on the app's own resources and catalog. That worker never ends the process: what keeps it from working it says in the log, in one line for a database that is away or not migrated, with the trace for anything else, and it tries again after `worker.TRIES_AGAIN_AFTER_S`, unless it was told to stop meanwhile. It is told to stop at the signal, at the moment the answers are (`told_to_stop` in `actio.app`), and only once, by cancelling its task: Procrastinate's worker takes a second cancellation as a cut, and the job in hand would lose its grace. A test fails if it is cancelled twice. The lifespan's exit tells it if nothing has, before the turns are drained, and waits for it while the resources are still open. `jobs.SHUTDOWN_GRACE_S` stays shorter than `WAITS_FOR_REQUESTS_S`. Its log is uvicorn's own plus one handler, for Actio's and the queue's records in the worker role's format, given to uvicorn as `log_config`, a deep copy of uvicorn's: with `--reload` the server runs in a process of its own, which sets up its log from that alone. `--role api` keeps uvicorn's log as it is. In `--role all`, `/api/readyz` also says `worker`, `ok` or `not working`, and answers 503 on the second. The worker works from a beat until `alive.STALE_AFTER_S` after its last one, the file check's rule, or until it ends with an error or can't work, whichever comes first: a run beats as soon as it starts, and `run_inside` starts a failed one again sooner than a beat goes stale. The last beat is kept in memory (`alive.LastBeat`), noted by `_WorkerInside` at the event loop's time through `run_inside`'s `on_beat`, beside the file, and forgotten through its `on_stopped`. The route asks through `app.state.worker_works`, `None` without a worker: `actio.api` imports neither `actio.app` nor `actio.worker`. Without a worker the key is left out, so `--role api` answers as before;

The route starts it through the `Runner` dependency, and only reads along. Whatever a reader is told goes into the turn's stream of events (`Events`), never straight into a response: someone who joins later gets it too;

A turn waits there in `actio.chat.answering`, after its beat has started and inside its `Halt`'s scope, so that it is alive and can be stopped while it waits. Its model is asked only once it has passed, and the place is given back as soon as the model's stream is closed;

The count is given back when the response is over, by the response itself (`_Reading` in `actio.api.turns`), not by the stream it reads, which may never begin;

  - a running turn says so every `turns.BEAT`, and saves with it, in the same statement, what its answer holds so far: its draft, on the turn's row, read and written through `turns.Draft` only. It is given up on after `turns.STALE_AFTER` of silence: by whoever looks at its conversation (`turns.give_up_on_stale`), and by the worker every ten minutes, in every conversation (`turns.give_up_on_stale_everywhere`, the job `worker.GIVE_UP`). The rule is written once, `_stale` in `actio.chat.turns`: whoever gives up goes through `_give_up` there, and `being_written` counts the running turns the rule leaves out. A turn given up on keeps its draft as its answer, dated at its last beat. Every ending is recorded through `_end` there, `finish`'s and giving up's, and empties the draft. Change the rule, or what giving up or ending does, there and never beside it. Giving up changes the conversation's row, so it holds that row, then the turn's: the order `ask` and `finish` take them. Whoever looks first asks, holding nothing, whether there is a stale turn at all. The worker takes the turns first, and never waits for a row's lock: it skips a turn, or a turn's conversation, that another transaction holds (`skip_locked`), and leaves it for its next run. What must not outlast a process that died, the hold on its credits and its stream, is kept by that beat and lasts as long without it, so nothing that gives up on a turn touches them;

Three waits have to fit inside each other, or a test in `deploy/tests/` fails: `GRACE` plus `LAST_WORDS`, then `WAITS_FOR_REQUESTS_S` in `actio.cli`, then `stop_grace_period` in `compose.yaml`. uvicorn takes a SIGINT that follows another signal for "quit at once", and skips the application's shutdown. Never the counters before the ledger: they are rebuilt from it;
  - what a settle couldn't tell the counters, the worker tells them again every ten minutes (`missed.count_missed`, the job `worker.COUNT_MISSED`, [ADR 0020](docs/adr/0020-usage-limits-on-turns.md), revision of 2026-11-20). It takes the notes older than `missed.COUNTED_WITHIN`, which is the writing process's own time to tell them, settles their rows again, and takes away each note the engine answered, whatever the answer: a repeated settle never counts twice. It stops at the first settle Valkey doesn't answer, and leaves the rest for its next run. A row the engine refuses to take loses its note too, with a warning: one row must not stop the rows behind it. The API and the worker take the engine from `Resources.quota`, so that they count under the same keys;
  - the usage ledger only takes new rows. The database refuses to change or delete one, so no code should try;
  - `Usage` is the limit on what answers cost, and `Limits` the limit on how often something is tried. A turn passes both, and a third: its plan's `answers_at_once`, how many answers one account may have being written at once. That one is checked in `actio.chat.turns`, counted from the turns' rows under an advisory lock per account, before anything is kept or held;
  - the proxy refuses a request's body over 2 MB on the API's routes, as a problem document: one that says its length before any of it is passed on, one sent in chunks once the limit is reached. A test in `deploy/tests/` holds that to `MAX_QUESTION_CHARS`, at twelve bytes a character: a change to either is a change to both;
  - the proxy compresses what the API answers as JSON, by the response's `Content-Type`, `application/json`, with gzip alone, for a client that takes it, once the body is over 512 bytes ([ADR 0004](docs/adr/0004-local-development-stack.md), revision of 2026-11-22). It leaves alone an answer's stream, problem documents (`application/problem+json`) and the web app's files, which Next compresses itself. A route that streams answers with the stream's media type, `ui_stream.MEDIA_TYPE`, and so stays out: gzip would make a stream larger, a few bytes at every event passed on at once, and hold a compressor for as long as its answer is written. A new kind of answer that should be compressed is JSON. Without the rule, a test in `deploy/tests/` and `apps/web/e2e/compressed.spec.ts` fail.
- **Documentation:** the site is built from `docs/` and from the package READMEs its pages include, by a Markdown reader that is stricter about lists than GitHub's. In those files a list starts after an empty line, and what belongs to an item (a sub-item, a table, a quote, a second paragraph) is indented by four spaces a level, not two. Written otherwise it looks right on GitHub and wrong on the site, so a check fails: `scripts/check_docs_lists.py`.
- **Decisions:** anything hard to reverse gets an ADR. Copy [`docs/adr/0000-template.md`](docs/adr/0000-template.md).
