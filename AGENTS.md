# AGENTS.md

Guidance for AI coding agents, and for humans, working in this repository.

## Project

Actio is a self-hostable, local-first AI platform. It combines a chat assistant, an OpenAI/Anthropic-compatible developer gateway, and Claude-inspired usage limits. Design decisions live in [`docs/adr/`](docs/adr/).

## Ground rules

- **Small steps.**
  - Make one focused, tested change at a time. There is no size limit: a step is done when it works end to end, with its tests.
  - Explain what changed, why, and how to verify it.
- **Humans commit.** Agents never commit, push, or create remote resources. The maintainer reviews and commits every change.
- **No secrets in the repo.**
  - Never commit `.env` files, keys or tokens.
  - Tests must never read `.env`; they use fakes and generated test config.
  - Commit hooks scan for secrets (gitleaks) and for private names listed in `~/.config/actio/denylist.txt`, which stays outside the repo.
- **Never bypass the checks.** Don't use `git commit --no-verify`; fix what the hook reports.
- **Written from scratch.**
  - Don't paste code from other projects.
  - Third-party code enters only as declared dependencies with compatible licenses: MIT, BSD, Apache-2.0 and similar permissive ones, or the LGPL for a library used unmodified ([ADR 0008](docs/adr/0008-postgres-through-sqlalchemy-and-psycopg.md)). No GPL or AGPL code.
  - Check a new dependency's license from its own metadata before adding it. If it reaches a container image under anything but a permissive license, list it in `THIRD_PARTY_NOTICES.md`.
- **Fictional data only.** Demo content, such as the "Velora Cycles" knowledge base, is fictional.

## Commands

| Command | What it does |
|---|---|
| `make help` | List available targets |
| `make doctor` | Check that required tools are installed. Prints install hints; installs nothing |
| `make bootstrap` | Set up a fresh clone: `doctor`, `install`, a `.env` with random passwords, then pull the images |
| `make install` | Install the Python and JavaScript workspaces with their dev tools, plus the git hooks |
| `make up` | Build and run the whole stack in containers, shaped like production, at http://localhost:8080 |
| `make dev` | Run the stack at http://localhost:8080 with the API and web app native, with hot reload. The worker runs inside the API's process (`--role all`), and reloads with it |
| `make smoke` | Check a running stack through Caddy: the web page, and that the API is healthy, ready (database migrated, Valkey answering, and under `make dev` the worker inside the API working), serves its docs, starts a guest session, lists its models and says what a guest may use |
| `make migration name="..."` | Write a new database migration from the table models, as a numbered draft to read and edit |
| `make openapi` | After a change to a route or a schema: record the API's description again (`apps/api/openapi.json`), and generate the web app's types from it (`apps/web/lib/api/schema.d.ts`). Review the difference |
| `make docs` | Preview the documentation site at http://localhost:8001, reloading on edits |
| `make down` | Stop all containers. Their data stays in Docker volumes |
| `make check` | Run what CI's main job runs: every static check on all files, the tests, then the builds (web app and docs site). The end-to-end tests are apart: `make e2e` |
| `make test-live` | Run the model-client tests against a real Ollama server (0.40 or newer, with `granite4:micro` pulled). Not part of `make check` |
| `make test-cloud` | Run the model client's tests of Groq and the Gemini API against the real servers instead of their recordings, with `GROQ_API_KEY` and `GEMINI_API_KEY` from the shell, or else `.env`, as `make preflight` reads them: about fifteen short requests, which count against the accounts' limits, two of them to `gemini-3.6-flash`, of which a free account had 20 a day on 2026-11-25. A provider without a key has its tests skipped, and `args="-k thoughts"` asks one exchange alone. `ACTIO_RECORD_CLOUD=1 make test-cloud` records them again: review the diff. Not part of `make check`, and CI doesn't run it |
| `make e2e` | Run the end-to-end tests: build and start a stack of its own (port 8090, its own data, a fake model), drive it in a real browser with Playwright, and remove it. Needs Docker; about a minute. Not part of `make check`: CI runs it as its own job. `make e2e args="--headed --workers 1"` passes arguments to Playwright, here to show the browser, one test at a time (the first such run downloads the whole of Chromium, about 200 MB). `ACTIO_E2E_KEEP=1` leaves the stack running, and `make e2e args=down` stops it |
| `make demo-record` | Record the README's hero GIF, `docs/assets/hero.gif`, from the stack that is running (`make up`, the page as people get it), whose model must answer: a headless Chromium asks the chat a question and turns the page dark (`apps/web/demo/record.mts`), and `scripts/demo_gif.py` makes one GIF of what it painted. Starts or stops nothing itself, and says in one line what is missing. Not part of `make check`. See "The README's GIF" in `docs/development.md` |
| `make preflight` | Read the models file with the API's own reader, the one `ACTIO_MODELS_FILE` names or else `config/models.toml` (`args="--models-file PATH"` names another), and ask each cloud provider what the account may use (`scripts/preflight.py`): each table of the file at Groq's host or the Gemini API's, with the key in the variable it names, from the shell, or else `.env`, and a provider the file has no table of with its own models and `GROQ_API_KEY` or `GEMINI_API_KEY`. That it takes the key, that the file's models on the table are offered to it, and that each answers one short question, at the provider's own address, which counts against the account's limits. Prints what it says of each model, the limits its answers state, and where to read those its API doesn't; holds the file's window, longest answer and Groq's requests a day and tokens a minute against what the provider states, and names each figure of the file it couldn't check. `make preflight args="groq=openai/gpt-oss-20b"` checks Groq alone, with that model. Fails when anything failed, a figure of the file larger than the provider's included, when no provider had a key, and when the file can't be read. A model whose provider was too busy to answer (503) is said and counted, and fails nothing: nothing is asked twice. Needs the network and the keys: not part of `make check`, and CI doesn't run it. See "The cloud providers' limits" in `docs/development.md` |
| `make fmt` | Format code and apply safe lint fixes |

`make lint`, `make test` and `make build` run the parts of `make check` on their own. The static checks are defined once, in `.pre-commit-config.yaml`, and run at every commit, in `make check` and in CI. Processes can also run alone: `uv run actio --role all --reload`, the API with the worker inside it, as `make dev` runs it, or `uv run actio --role api --reload` without the worker, `uv run actio --role worker`, which runs the background jobs alone, `pnpm --dir apps/web dev`, or the fake LLM server with `uv run fakellm`. `uv run actio-llm chat <model> "<prompt>"` talks to a local model through the Ollama adapter. The web app is tested at two levels: its components in a simulated browser, against a fake API (`make test`), and the whole stack in a real browser, with a fake model (`make e2e`). A change to the chat should pass both, and be looked at once at http://localhost:8080.

`make up` needs only Docker; it builds the images from `apps/api/Dockerfile`, which the migration job and the worker run too, `apps/web/Dockerfile` and `deploy/caddy/Dockerfile`, the proxy with its config. `make dev` stops the worker's container, and builds the proxy's image too, so a change to `deploy/caddy/Caddyfile` takes effect when either is run again. `make dev` needs Docker Desktop: its containers reach the natively running API and web app through `host.docker.internal`. Changes to the containers must keep `deploy/tests/` passing; if a rule must change, change the test on purpose and record why in an ADR. `.env` holds the local passwords. It is created once from `.env.example`, git-ignored, and never read by tests. Postgres keeps the password it first started with, so if you recreate `.env`, also wipe the local data with `docker compose down --volumes`.

## Conventions

- **Python:**
  - 3.13, managed with `uv`;
  - add dependencies with `uv add`, never `pip`; run tools through `uv run` or `make`;
  - workspace packages are named `actio-<name>` and imported as `actio_<name>`, such as `actio-fakellm`;
  - formatted and linted with `ruff`;
  - `mypy --strict` on core packages;
  - tests with `pytest`; property and state-machine tests with Hypothesis (`HYPOTHESIS_PROFILE=dev|ci|nightly`);
  - `make test` fails below 90% coverage of `packages/quota`, and needs Docker running: the quota and API tests start throwaway Valkey and Postgres containers;
  - a change to a table model needs a migration in the same commit (`make migration name="..."`): a test fails when the models and the migrations disagree. Never edit a migration that is already on `main`; write the next one;
  - the queue of background jobs is Procrastinate's, pinned to an exact version: migration 0009 builds its tables from the package's own SQL files, up to that version ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md)). An upgrade is a new pin and a new migration that applies the package's files after the version the last one names. A test that compares the queue with the package's `schema.sql` fails until both are there;
  - `apps/api/src/actio/core` imports nothing else from `actio`;
  - a file in `config/` is read through `actio.core.config_file`, which says a mistake in it in one line. The API's command line reads each such file before starting, so a mistake stops it there;
  - in the API's tests a credit is a token and the usage limits are out of reach. A test that wants to reach one asks for plans, `plans_with(guest=(1_000, 10_000))`, and a `ScriptedModel`'s last event says what a turn used. The limit on answers at once is out of reach too, unless asked for: `plans_with(answers_at_once=1)`. A test that needs other prices states them as a plans file would: `plans_with(prices={"standard": {"input": 250_000, "output": 1_000_000}})`. A test of the gate in front of a model's server offers its models through `lineup`, each with a script of its own, behind a `Gate` it chooses, and one that is more than its script, such as a model whose server can load it ahead, through `lineup.offer`. Each way in names whose answer it is: a test that holds a place itself, or puts an answer at the gate by hand, passes an account of its own (`gate.passing(account)`), and a test of whose turn passes first asks as two or three guests, in one browser whose session it changes once a request has reached the app. So does a test of the models that stand in for one: `then` names them, `state` makes a model one its server says isn't ready, and `tokens_a_minute` or a small `context_window` gives it a room smaller than a long question. What its server says of it can change while the test runs (`lineup.becomes`), and its answer can be held (`lineup.hold`, whose `answers` the test sets), to show what waited for it and what didn't: `lineup.asked` names each ask, `asks_ended` waits for those that run behind a request, and an app that shuts down, or `Catalog.stop_tasks`, ends one held for ever. `budget` gives a model a budget, from the figures a models file would state, such as `budget={"requests_a_day": 1}`, which two models share when they have the same name on their server (`on_server`): a test fills it, and reads back what a turn took, through a `Budgets` under the app's own prefix, `{settings.valkey_prefix}:b`, at the test's `clock`. A key in Valkey expires in real time while the test's `clock` is moved by hand, so a bucket's period is a minute or a day, as a provider's is, and never shorter. Each model of a `lineup` has a breaker too, which two models with the same name on their server share, kept for as long as the lineup lives: a test opens it with turns whose model fails, or by its own tries at the test's `clock` (`lineup.catalog().get(name).breaker`), and ends its wait by moving that `clock`, never by sleeping. So does the wait each model's provider named, shared and kept as the breaker is: a test has it told by turns whose model raises a `RateLimitedError` with a `retry_after_s` longer than 2 s, or tells it itself at the test's `clock` (`lineup.catalog().get(name).own_wait.told(...)`), and ends it by moving that `clock`;
  - a test of an answer that is still being written starts the request as a task, waits for `model.waiting` (a `ScriptedModel` held at an `asyncio.Event` of its script), acts, and looks at the response afterwards: in process a response comes back whole. Only what takes a connection that closes goes in `test_turns_live.py`. A request that could wait for ever on a broken app gets a time limit, so the test fails instead of hanging;
  - a test of background jobs defers them through its database session, and runs them with `work_through(jobs.Job(...))`: a worker in the test's process that returns once nothing is left. One that needs a worker that waits starts `jobs.work(..., on_signals=False)` as a task and cancels it, which stops it as the process's signal does. A test of the signals themselves sends real ones to its own process, with a handler of its own in place first, and puts back what it found, pass or fail. The real process, and its signals, are tested in a subprocess (`test_worker.py`). A test of the worker's beat makes it short: `monkeypatch.setattr(alive, "BEAT_S", 0.05)`. A test of the worker inside the API opens the app with `open_app(settings, with_worker=True)`, which runs the jobs of `worker.listed`: the test replaces that list with jobs of its own, and defers before the app starts, since a job committed in the instant a worker starts can wait five seconds for its next look (`test_all_role.py`). A test of the look after the queue writes what a dead worker leaves through `queue_books`, from a job of its own that runs before the look: a worker that starts takes the dead ones off the list itself. A job put back after an error is dated by its worker's clock, and a worker that waits looks for it only every five seconds: so a test of one gives its listing waits of a minute or more, which never end by themselves while it runs (the title job's tests use its own, half a minute at the least), reads in how long the job is due (`queue_books.due()`, by the test process's own clock, which dated it), ends the wait through the database (`queue_books.wait_is_over()`), and runs a worker again. None sleeps through a wait;
  - change the Lua in `packages/quota` only together with the Python reference model (`oracle.py`): the differential test requires both to behave identically;
  - the same holds for the rate limiter's script, `apps/api/src/actio/core/rate_limit.lua`, and the plain token buckets in `apps/api/tests/test_rate_limit.py`;
  - and for the budgets' script, `apps/api/src/actio/core/budget.lua`, and the plain buckets in `apps/api/tests/test_budget.py` (`PlainBuckets`), counted exactly, which the script must agree with to within its rounding to the millisecond: less than one for each add since the bucket was last surely full, and one more for a look;
  - new HTTP client code uses `httpx2`, the maintained continuation of httpx ([ADR 0007](docs/adr/0007-local-models-through-ollamas-native-api.md)). The older test fixtures that call an app in-process still use httpx. Where a model client reads a body (`actio_llm.wire`), it catches the client's `DecodingError` by its own name beside its errors of the connection: a body that can't be unpacked is none of those (`TransportError`), and let out as it was it failed the list of models (revision of 2026-11-23);
  - the Ollama adapter's tests replay recorded exchanges (`packages/llm/tests/fixtures/ollama/`), and fail if the request it sends changes. After changing what it sends, run `ACTIO_RECORD_OLLAMA=1 make test-live` to record them again from a real server, and review the diff;
  - so do the OpenAI-compatible adapter's tests of Groq and the Gemini API (`fixtures/groq/`, `fixtures/gemini/`, [ADR 0027](docs/adr/0027-cloud-models-through-their-openai-compatible-layers.md)), which compare what it yields with the recorded lines, read apart from it. `ACTIO_RECORD_CLOUD=1 make test-cloud` records them again with your keys, tidied as they are written: no header of a request, and Groq's ids of a request and of a chat completion, the account's organization and thought signatures replaced by stand-ins. A test fails at another organization's id, a longer signature or a header named `authorization`. The five that depend on the account's or the provider's state, a limit reached or a model too busy, before an answer or in the middle of one, were written from real answers and are never asked live;
  - what a turn streams is recorded too, in `apps/api/tests/fixtures/turns/`, and the web app's tests read those files with the real `ai` package ([ADR 0014](docs/adr/0014-turns-streamed-in-the-ai-sdks-format.md)). After changing the stream on purpose, run `ACTIO_RECORD_TURNS=1 uv run pytest apps/api/tests/test_turn_fixtures.py`, review the diff, then `pnpm --dir apps/web run test`. The refusal of a turn at a usage limit is recorded beside them (`limit_reached.json`), and so is the refusal of a turn that no model has budget left for (`no_budget.json`, from a `lineup`), and both change the same way. So do a stream that ends because its turn was stopped (`stopped.sse`), one with the line that keeps a silent connection open (`keep_alive.sse`), what someone who reads along is sent when the turn's stream is gone (`lost.sse`), and a turn with every figure the page shows under an answer, from a model that says how long it took to write and a clock that moves (`figures.sse`), and an answer of no words that was counted all the same (`no_words.sse`), and an answer its model was still writing when its server's time for a whole answer was over (`took_too_long.sse`), and an answer by a model that stood in for the one asked, with a window of its own (`stood_in.sse`, from a `lineup`), and an answer that waited at its model's gate behind two answers, then one, before its turn came (`waited.sse`, from a `lineup` whose gate the test holds a place at). A `ScriptedModel` calls a function in its script where it stands, such as one that moves the test's `clock`.
- **TypeScript:**

- **API conventions:**
  - routes live in `actio.api`; rules and tables live in a domain module below it, which never commits: the route decides when the unit of work is done;
  - a request's body is a `Body` (`actio.api.body`), never a bare `BaseModel`: a test fails otherwise. A body is JSON, which can spell two kinds of character that can't be stored: U+0000, and half of a surrogate pair, as an emoji cut in two leaves it. `Body` puts U+FFFD in the place of each, in every string and every member's name down to sixteen levels, far below any request, before anything reads the request (`actio.core.text.storable`, [ADR 0008](docs/adr/0008-postgres-through-sqlalchemy-and-psycopg.md), revision of 2026-11-20). What a model writes gets the same where it comes in: an answer in `Answer` (`actio.chat.answering`), before a reader is shown it. Text from a new source, such as a tool's result or a file, goes through `storable` where it comes in too, not where it is stored. The refusal of a body (422) says where it is wrong and never repeats what was sent, and has to stay so: a string below those sixteen levels wasn't looked at. An address for a new account that holds the mark is refused (`SignUp`): the rules for an address would take it;
  - a model defined in `actio.api`, one the API takes or answers with, is a `Described` (`actio.api.described`), never a bare `BaseModel`: a test fails otherwise. `Body` is one. A part of a message is defined below `actio.api` and can't be one (`actio.chat.parts`): what is written under its members isn't published. The string under a member of a `Described` is that member's description in `/api/docs`, in `apps/api/openapi.json` and in the web app's generated types, so write it for a reader of the API: what the member means, not how it is made, and with no name from the code in it. After changing one, run `make openapi`;
  - errors are RFC 9457 problem documents: raise `Problem(status, detail)`. `detail` is shown to people as it is, so write it for them;
  - a route lists the errors it answers in its `responses`, with a description each. The `Problem` schema is filled in for them. A route that takes `CurrentPrincipal` passes `NO_SESSION`, or its router does: a test fails otherwise;
  - the API's description is recorded in `apps/api/openapi.json`, and the web app's types are generated from it. After changing a route or a schema, run `make openapi` and review the difference: tests on both sides fail until then;
  - reading a conversation whole takes several queries. Call `conversations.hold_still` first, so a turn that ends meanwhile isn't seen half ([ADR 0014](docs/adr/0014-turns-streamed-in-the-ai-sdks-format.md), revision of 2026-11-13);
  - a conversation's branch is picked out of its messages in the code (`tree.branch_to`): one statement reads the conversation's messages, each once, and the code walks up from the last one ([ADR 0012](docs/adr/0012-conversations-as-a-tree-of-messages.md), revision of 2026-11-24). Never by a query that joins each message to its parent inside the database: how that runs is the planner's choice, and it read the whole conversation again at every step, 360,000 rows for a branch of 600, for whoever opened the conversation and before every answer in it. A test in `apps/api/tests/test_conversations.py` asks the database how it ran the read (`EXPLAIN (ANALYZE, FORMAT JSON)`), and fails when it took a message from the table more than once. The walk down, to show another branch, is still the database's (`tree.show_branch_through`): timed once, at 1 to 2 ms down a branch of 600, and held by no test. A new read that walks or joins inside the database is timed with a long conversation among many short ones before it is trusted: a fresh database of a few long conversations ran the old query well;

  - a job that follows a change is deferred in that change's transaction, by its name: `await jobs.defer(db, "name", ...)` (`actio.core.jobs`), which never commits. It is there once the transaction commits, and never if it is rolled back. A job the database refuses raises `jobs.DeferError`, one of SQLAlchemy's errors, as any failed statement of the session does. Its arguments are JSON, and Procrastinate writes them in the log: ids, not what people wrote. Its handler is listed in `actio.worker`, with what it needs bound in; a job whose name no worker lists ends as `failed` ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md)). The worker is a top layer like the API: it reads the clock, and passes it on as `now`;
  - a job's handler is safe to repeat: a job may run more than once, from its start each time ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md), revision of 2026-11-20). A stop that cuts it off at the end of its grace puts it back into the queue, and so does the worker's look after the queue when the worker that had it died. The scheduled jobs that change rows each take a batch of what is left to do, which a second run doesn't find again, and the comparison of the usage counters changes nothing; the title job looks first whether its conversation still wants one. With more than one worker, a job could also run twice at once, when a worker that was only late is taken for dead: so a handler takes what it works on in a way that a second run beside it doesn't, as the batches' `SKIP LOCKED` does;
  - a job that fails is not run again, unless its listing names the error as worth another try: `jobs.Job(name, run, again=jobs.Again(errors=(SomeError,), waits=(…)))`, the first wait before the first time it is run again, and the last serving any time after it ([ADR 0024](docs/adr/0024-background-jobs-in-a-queue-in-postgres.md), revision "a job is run again after an error its listing names"). List an error of the handler's own, and only one that may be gone at a later try: a database that refused a statement, or a mistake in the code, comes back each time. The handler says in the log what went wrong, in one line, before it raises: the queue's line for a job put back carries no trace, and names no error. It raises the error without its cause (`from None`), and its text holds kinds and ids, never what people wrote: the last try fails the job, and its trace, a cause's text included, is in the log;

A load takes no place at the gate: a question to the same model asked during one passes at once, and waits inside the server for it. A load that a model's server fails is a warning that names the error's kind, never its text; a mistake in Actio's own code there is logged with its trace. The worker never loads ahead. Without these, tests in `packages/llm/tests/test_ollama.py`, `test_catalog.py` and `test_warm_up_api.py` fail;
  - a reader is counted against its account, over both routes that stream (`Readers`, `actio.chat.readers`): one who joins is refused past `READERS_PER_ACCOUNT`, and the reader of the request that starts a turn never is. The count is given back when the response is over, by the response itself (`_Reading` in `actio.api.turns`), not by the stream it reads, which may never begin;
  - a route that streams takes what it needs from the database and commits before the stream begins. A reader holds no database connection while it reads: a test fails otherwise;
  - a turn ends early only through its `Halt` (`actio.chat.answering`): `runner.stop`, for whoever asked, or the shutdown. Nothing cancels a turn's task, and nothing takes a closed connection for a stop;
  - a running turn says so every `turns.BEAT`, and saves with it, in the same statement, what its answer holds so far: its draft, on the turn's row, read and written through `turns.Draft` only. It is given up on after `turns.STALE_AFTER` of silence: by whoever looks at its conversation (`turns.give_up_on_stale`), and by the worker every ten minutes, in every conversation (`turns.give_up_on_stale_everywhere`, the job `worker.GIVE_UP`). The rule is written once, `_stale` in `actio.chat.turns`: whoever gives up goes through `_give_up` there, and `being_written` counts the running turns the rule leaves out. A turn given up on keeps its draft as its answer, dated at its last beat. Every ending is recorded through `_end` there, `finish`'s and giving up's, and empties the draft. Change the rule, or what giving up or ending does, there and never beside it. Giving up changes the conversation's row, so it holds that row, then the turn's: the order `ask` and `finish` take them. Whoever looks first asks, holding nothing, whether there is a stale turn at all. The worker takes the turns first, and never waits for a row's lock: it skips a turn, or a turn's conversation, that another transaction holds (`skip_locked`), and leaves it for its next run. What must not outlast a process that died, the hold on its credits and its stream, is kept by that beat and lasts as long without it, so nothing that gives up on a turn touches them;
  - told to stop, the API ends the answers that are being written itself, while their readers are still connected: it hears the signal before the web server does (`actio.core.signals`), gives the answers `GRACE`, and halts the rest (`actio.chat.running`). Three waits have to fit inside each other, or a test in `deploy/tests/` fails: `GRACE` plus `LAST_WORDS`, then `WAITS_FOR_REQUESTS_S` in `actio.cli`, then `stop_grace_period` in `compose.yaml`. uvicorn takes a SIGINT that follows another signal for "quit at once", and skips the application's shutdown. So a server that another process started, as uvicorn's reloader does in `make dev`, takes the first signal only, and later ones change nothing (`on_stop_signal(..., once=True)`, asked for in `actio.app`): there a Ctrl-C arrives several times over, from the terminal, from concurrently and from the reloader ([ADR 0022](docs/adr/0022-turns-that-run-apart-from-their-request.md), revision of 2026-11-19). A test starts the reloader for real, and fails if the application isn't shut down;
  - a route that needs to know who is asking takes `CurrentPrincipal`;
  - what belongs to an account is looked up with the account's id, in the query itself. Someone else's row answers 404, like one that doesn't exist: see `OwnConversation` in `actio.api.conversations`;
  - a route that anyone can call, or that checks a password, counts the attempt before doing its work: it takes `Limits` and calls one, such as `await limits.log_in(email)` ([ADR 0011](docs/adr/0011-rate-limits-as-token-buckets-in-valkey.md)). A new limit is a method in `actio.api.rate_limits` and a `limit_*` setting, listed in `compose.yaml` and `.env.example` too, or a test fails;
  - a module that defines tables is named `models` and listed in `actio/tables.py`, or a test fails. So nothing else is named `models`: the models people chat with are the `catalog`;
  - a model is asked for by its name in `config/models.toml`, through the `Models` dependency: `catalog.get("standard")`. Nothing outside `actio.catalog` names a provider's own model, or builds a client for one;
  - a model on offer needs a price in `config/plans.toml`, under the same name, or the API doesn't start. The same goes for the pair of files in `deploy/e2e/config/`. `GET /api/models` says each model's price, its own by its name, never a stand-in's, joined in the route from the plans (`usage.plans.price_of`), with `cached_input` the price of `input` where the file states none (`PriceOut` in `actio.api.catalog`);
  - whatever costs credits goes through `actio.usage.limits`, taken as the `Usage` dependency, in this order ([ADR 0020](docs/adr/0020-usage-limits-on-turns.md)): `reserve` before the work, in the transaction that starts it, so that a refusal leaves nothing behind; `record` in the transaction that writes how the work ended, which adds the ledger's row with its `Uncounted` row, the note that the counters haven't been told of it yet; only after that is committed, `settle`, or `release` when nothing was used; and after a `settle` that told the counters, which is any that didn't return `None`, `counted`, which takes the note away in a short transaction of its own that must not fail the work. Never the counters before the ledger: they are rebuilt from it;
  - what a settle couldn't tell the counters, the worker tells them again every ten minutes (`missed.count_missed`, the job `worker.COUNT_MISSED`, [ADR 0020](docs/adr/0020-usage-limits-on-turns.md), revision of 2026-11-20). It takes the notes older than `missed.COUNTED_WITHIN`, which is the writing process's own time to tell them, settles their rows again, and takes away each note the engine answered, whatever the answer: a repeated settle never counts twice. It stops at the first settle Valkey doesn't answer, and leaves the rest for its next run. A row the engine refuses to take loses its note too, with a warning: one row must not stop the rows behind it. The API and the worker take the engine from `Resources.quota`, so that they count under the same keys;
  - every hour at five past, the worker compares the usage counters with the ledger (`drift.compare`, the job `worker.COMPARE_USAGE`, [ADR 0020](docs/adr/0020-usage-limits-on-turns.md), revision of 2026-11-22), and says in its log how far apart they are, a line at every run at least, so that a run can be told from none. It only says: it writes nothing, to the database or to Valkey, not even a key's expiry, which the engine's two reads for it, `users` and `buckets`, leave alone. It compares the accounts that have counters, `drift.ACCOUNTS` at most a run, and the windows they have stored that are still open, without a plan: the worker has no plans file. Its reads go in the order that keeps an answer that ends meanwhile from showing as a difference: the counters, then the account's rows of the ledger, each with whether its note is still there, in one statement, then the counters once more for a window that seems short. The session reads what was committed since its transaction began, as READ COMMITTED does. A row whose note is still there is no difference. Without the second read of the counters, or with one snapshot for the whole run, a test in `test_usage_drift.py` fails. Valkey that doesn't answer stops the run without failing it, as for `count_missed`: only what the engine's own reads raise is taken for that, and an error of the database is raised as it is, whatever its kind. An id under the prefix that can't be an account's, not being a UUID as the API writes one, is left out with a warning;
  - the usage ledger only takes new rows. The database refuses to change or delete one, so no code should try;
  - `Usage` is the limit on what answers cost, and `Limits` the limit on how often something is tried. A turn passes both, and a third: its plan's `answers_at_once`, how many answers one account may have being written at once. That one is checked in `actio.chat.turns`, counted from the turns' rows under an advisory lock per account, before anything is kept or held. A fourth is not the account's but the installation's: the budgets of the models' providers, by which a turn is refused for now (above);
  - the proxy refuses a request's body over 2 MB on the API's routes, as a problem document: one that says its length before any of it is passed on, one sent in chunks once the limit is reached. A test in `deploy/tests/` holds that to `MAX_QUESTION_CHARS`, at twelve bytes a character: a change to either is a change to both;
  - the proxy compresses what the API answers as JSON, by the response's `Content-Type`, `application/json`, with gzip alone, for a client that takes it, once the body is over 512 bytes ([ADR 0004](docs/adr/0004-local-development-stack.md), revision of 2026-11-22). It leaves alone an answer's stream, problem documents (`application/problem+json`) and the web app's files, which Next compresses itself. A route that streams answers with the stream's media type, `ui_stream.MEDIA_TYPE`, and so stays out: gzip would make a stream larger, a few bytes at every event passed on at once, and hold a compressor for as long as its answer is written. A new kind of answer that should be compressed is JSON. Without the rule, a test in `deploy/tests/` and `apps/web/e2e/compressed.spec.ts` fail.
- **Documentation:** the site is built from `docs/` and from the package READMEs its pages include, by a Markdown reader that is stricter about lists than GitHub's. In those files a list starts after an empty line, and what belongs to an item (a sub-item, a table, a quote, a second paragraph) is indented by four spaces a level, not two. Written otherwise it looks right on GitHub and wrong on the site, so a check fails: `scripts/check_docs_lists.py`.
