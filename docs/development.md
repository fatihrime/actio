# Development

## Toolchains

- **Python 3.13 with uv.** One workspace (`apps/api`, `packages/fakellm`, `packages/llm` and `packages/quota`), one lockfile, and uv's own CPython build. See [ADR 0002](adr/0002-python-workspace-with-uv.md).
- **TypeScript with pnpm 12.**
    - pnpm also installs the pinned Node.js, 26 LTS.
    - TypeScript stays on 6.0 and ESLint on 9 until the linters support the next major versions.
    - See [ADR 0003](adr/0003-web-app-on-nextjs.md).
- **Docker Compose** for the local stack and the images. See [ADR 0004](adr/0004-local-development-stack.md) and [ADR 0005](adr/0005-container-images.md).

Add dependencies with `uv add` or `pnpm --dir apps/web add`, never with pip or npm.

## Checks

`make check` runs what CI's main job runs: every static check on every file, then the tests, then the builds. The end-to-end tests are apart, because they build and start the whole stack: `make e2e`. `make install` sets up the same static checks to run on the files of each commit:

| Area | Checks |
|---|---|
| Every file | Whitespace, line endings, merge markers, file size, YAML and TOML syntax |
| Python | Ruff (lint and format), mypy in strict mode, import rules (import-linter) |
| Web app | Prettier, ESLint with typescript-eslint's strict type-checked rules, `tsc` |
| Shell scripts | shellcheck |
| Docker Compose | `docker compose config` |
| GitHub Actions | actionlint, zizmor |
| This site's pages | Lists written so that the site shows them as lists: see [This site](#this-site) |
| Secrets | gitleaks, plus a private denylist of names that must never appear |

`make fmt` applies formatting and safe fixes. Don't bypass a failing check with `git commit --no-verify`; fix what it reports.

### Import rules

Actio is one application split into modules, not into services ([ADR 0001](adr/0001-one-app-several-process-roles.md)), so a tool keeps the modules apart. The rules live in `pyproject.toml`, under `[tool.importlinter]`, and `uv run lint-imports` checks them:

- the packages under `packages/` never import the application, or each other;
- inside the application, imports only point down the layers: `cli`, `app`, then `api` and `worker` side by side, `tables`, `chat`, then `catalog`, `identity` and `usage` side by side, `core`. `api` and `worker` are two ways into the same modules, and don't import each other. `chat` is above `identity` because a conversation belongs to an account, and above `usage` because a turn is paid for; `catalog`, `identity` and `usage` don't import each other;
- only `api`, the HTTP interface, imports the web framework. `core`, the domain modules and `worker` never do, because processes that serve no HTTP use them too;
- only `core.jobs` imports Procrastinate, the job queue's library, so that replacing it means rewriting one module ([ADR 0024](adr/0024-background-jobs-in-a-queue-in-postgres.md));
- every module directly under `actio` must be given a layer. A new module fails the check until someone decides where it belongs.

A broken rule names the file, the line and the import, and says what to do instead.

`make test` runs them all. Tests never read `.env`: they build their own settings.

- **Coverage gate:** `make test` fails if the quota engine's test coverage drops below 90%.
- **Docker:** the quota engine's tests need Valkey, and the API's tests need Postgres and Valkey. They start throwaway containers, from the images pinned in `compose.yaml`, once per run. Each API test gets its own empty database in that Postgres, and its own key prefix in that Valkey, so what one test counts against a limit the next doesn't inherit.
    - Without Docker, `uv run pytest` skips those tests; `make test`, and so CI, sets `ACTIO_REQUIRE_DOCKER=1`, so there they fail with the reason instead.
    - Set `ACTIO_TEST_VALKEY_URL` or `ACTIO_TEST_POSTGRES_URL` to use a server you already run.
- **Usage limits in the API's tests:** the app under test gets plans of its own, in which a credit is a token and the limits are out of reach. A test that wants to reach one asks for it: `plans_with(guest=(1_000, 10_000))`, or `plans_with(answers_at_once=1)` for how many answers may be written at once. A scripted model's last event says what a turn used, so a test chooses what the turn costs.
- **Models behind a gate, in the API's tests:** the fixture `lineup` offers models of a test's own, each with a script, on servers the test chooses: `lineup.add("second", TextDelta("…"), DONE, gate=gate)`, where a `Gate(1)` is a server that writes one answer at a time. A test asks one of them by its name, and starts the app with `lineup.catalog()`.
- **Answers that are still being written, in the API's tests:** a turn runs apart from its request, so a test starts the request as a task and acts while the model is held half-way.
    - A `ScriptedModel` waits at an `asyncio.Event` in its script, and sets `waiting` when it has got there: everything before it has been stored and streamed by then.
    - A response in process comes back whole, once its stream has ended. What only a connection that closes can show is in `test_turns_live.py`, against a real server.
    - `open_app` gives an app the test shuts down itself, to see what a shutdown records. Under test a shutdown doesn't wait for answers, and a beat comes every 15 real seconds, which no test waits for: a test of either sets its own (`running.GRACE`, `turns.BEAT`).
- **Background jobs, in the API's tests:** a test defers jobs through its database session, as the code does, and `work_through(jobs.Job("name", handler))` runs a worker in the test's process, which returns once nothing is left to run. A test that needs a worker that waits starts `jobs.work(…, on_signals=False)` as a task, and cancels it: that stops it as the process's signal does, and leaves the test run's own signals alone. A test of the signals themselves sends real ones to its own process, with a handler of its own in place first, so that a worker that doesn't listen can't stop the test run; it puts back what it found, pass or fail. A worker says every five seconds that it works; a test of that makes it a twentieth of a second, `monkeypatch.setattr(alive, "BEAT_S", 0.05)`. `open_app(settings, with_worker=True)` gives an app with the worker inside it, as `--role all` runs it. Such a test replaces the worker's list of jobs with its own, and defers before the app starts: a job committed in the instant a worker starts can wait five seconds for its next look.
- **One format, tested from both sides:** the API streams answers in the format of a JavaScript library, the AI SDK. The API's streams are recorded in `apps/api/tests/fixtures/turns/`: a Python test fails when the API stops producing exactly those files, and a test in `apps/web` reads the same files with the library itself. After changing the stream on purpose, record them again with `ACTIO_RECORD_TURNS=1 uv run pytest apps/api/tests/test_turn_fixtures.py`, review the difference, and run the web app's tests. See [ADR 0014](adr/0014-turns-streamed-in-the-ai-sdks-format.md).
- **One description of the API, checked from both sides:** the API's description of itself (OpenAPI) is recorded in `apps/api/openapi.json`, and the web app's types in `apps/web/lib/api/schema.d.ts` are generated from it. A Python test fails when the API no longer matches the file, and a test in `apps/web` fails when the types no longer match it. After changing a route or a schema on purpose, run `make openapi`, which writes both again, and review the difference. The TypeScript compiler then points at every call in the web app that no longer fits. See [ADR 0015](adr/0015-the-web-chat-calls-the-api-from-the-browser.md).
- **The chat's tests never reach a network.** They render the real components and replace `fetch` with a fake API (`apps/web/tests/fake-api.ts`). It answers with the recorded streams above, and with bodies typed by the generated types, so a test can't run on an answer the API wouldn't give. A request that a test set up no answer for fails that test.
    - A question at a usage limit is answered with the refusal the API was recorded giving, `limit_reached.json`, which is kept true the same way as the streams.
    - A test that shows a time of day, or waits for a moment, sets the clock (`apps/web/tests/clock.ts`). Timers still run in real time, so the page is driven as ever. The tests run in one time zone, UTC, on every machine.
    - The simulated browser paints frames by itself. A test that says when the next one comes holds them (`apps/web/tests/frames.ts`).
- **End to end, in a real browser:** `make e2e` builds the images and starts a stack of its own, as `make up` would, with [fakellm](reference/fakellm.md) as one more container in Ollama's place. Playwright then drives it in a headless Chromium (`apps/web/e2e`), and the stack is removed again. See [ADR 0017](adr/0017-end-to-end-tests-on-the-real-stack.md).
    - It runs beside your own stack, on port 8090 with its own data, and reads no `.env`.
    - A test scripts the model by typing: `[[pace: 0.1]]` makes an answer take its time, `[[fail: 503]]` makes it fail.
    - The fake's quiet model names conversations there. It says nothing, so a conversation keeps its first line, unless its question carries `[[say: Flat tyres]]`, the title to write.
    - Every test also fails if the page asks anything of another site, or if a script on it breaks.
    - An account's usage limit is within reach there: 500 credits a session, at a credit a word. A test of the limits signs up and asks long questions. A guest's limit is out of reach.
    - A guest may have two answers being written at once there, and an account three, as people get. The fake model has no gate in front of it, so the tests run side by side.
    - It needs Docker and about a minute, so it isn't part of `make check`. The first run downloads the browser, about 90 MB.
    - To work on a test: `ACTIO_E2E_KEEP=1 make e2e` leaves the stack running, and `pnpm --dir apps/web exec playwright test` runs the tests against it again. `make e2e args=down` stops it. `make e2e args="--headed --workers 1"` shows the browser, one test at a time; the first such run downloads the whole of Chromium, about 200 MB more. A failed test leaves a trace in `apps/web/test-results/`, to open with `pnpm --dir apps/web exec playwright show-trace`.
- **Real models:** `make test-live` runs the model-client tests against a real Ollama server instead of the recordings. It needs Ollama 0.40 or newer with `granite4:micro` pulled, so it isn't part of `make check`. See the [model clients reference](reference/llm.md#tests).
- **Nightly:** a scheduled workflow runs the quota tests with 5,000 random examples each.
- **Random tests:** Hypothesis tries 100 random examples per property on a laptop and 200 in CI. Set `HYPOTHESIS_PROFILE=nightly` for 5,000. When a test fails, Hypothesis shrinks it to a minimal sequence of steps and prints it.

## Database migrations

The schema's history is in `apps/api/src/actio/migrations/versions/`, one numbered file per change ([ADR 0008](adr/0008-postgres-through-sqlalchemy-and-psycopg.md)).

1. Change or add a table model.
2. Run `make migration name="what it does"`. It compares the models with a migrated database and writes the difference as the next numbered file.
3. Read that file: it is a draft. Check both `upgrade` and `downgrade`.
4. Commit the model and the migration together.

- `make dev` and `make up` apply pending migrations before the API and the worker start. `uv run actio --role migrate` does it by hand.
- A test fails when the models and the migrations disagree, and another undoes every migration.
- Never edit a migration that is already on `main`: databases have applied it. Write the next one.
- The job queue's tables are Procrastinate's: no model describes them, and the comparison with the models leaves them out. Migration 0009 builds them from the package's own SQL files, up to the version it is pinned to. Upgrading Procrastinate takes a migration of its own, which applies the files after that version; a test fails until it is there ([ADR 0024](adr/0024-background-jobs-in-a-queue-in-postgres.md)).

## The README's GIF

`make demo-record` records the GIF at the top of the README, `docs/assets/hero.gif`, from the stack you run: a question asked in the chat and answered, then the page turned dark.

- **What it needs:** the stack at <http://localhost:8080>, from `make up`, which is the page as people get it, with a model that answers. It starts and stops nothing itself. When something is missing it says so in one line: that nothing answers at that address, or what the page says when no answer comes. `ACTIO_DEMO_URL` points it at another address.
- **What it leaves:** each run adds two guests and a conversation each to that stack's database. The first asks a short question before the recording, so that the model is loaded by the time the recorded question reaches it. The first run downloads Chromium's headless build, as `make e2e` does.
- **How it is made:** `apps/web/demo/record.mts` drives the page in a headless Chromium, 960 by 600 pixels and light, and saves each picture Chromium paints, with the moment it was painted (Chromium's screencast). `scripts/demo_gif.py` makes one GIF of them, which loops for ever: frames at least 66 ms apart, each shown until the next was painted, 1.5 s at the most, the last one for 3 s, and all of them with the same 256 colours. It ends by saying how many frames the GIF has, how long it lasts and how large it is, and fails when it is heavier than 1.5 MB, with the GIF written all the same, to be looked at. A recording weighs about 0.6 MB. The commit hook that keeps files over 500 kB out of git makes an exception of this one path (`.pre-commit-config.yaml`), so nothing at a commit holds its size: read what the target says before you commit the file.
- **To change what it shows:** the question is at the top of `apps/web/demo/record.mts`, and the steps and the pauses between them are in its `record`, in the order they happen, with the window's size and colours where its browser context is made. How the frames become a GIF is in the constants at the top of `scripts/demo_gif.py`, and its tests in `scripts/tests/test_demo_gif.py`.
- The recorder is TypeScript that Node runs as it is, stripping the types itself, so `make lint` checks it as it checks the rest of the web app. Neither Vitest nor `make e2e` runs it.
- A model's answer changes from one run to the next, and so does the GIF. Look at it before you commit it.

## The cloud providers' limits

Actio can send answers to the free tiers of two cloud providers, Groq and Google's Gemini API, beside the local Ollama: `config/examples/free-cloud` offers their models ([ADR 0027](adr/0027-cloud-models-through-their-openai-compatible-layers.md)). What a free tier allows is set for each account, and changes. `make preflight` asks each provider what your own account may use, before anything relies on it.

- **What it needs:** a key for each provider to check, in `GROQ_API_KEY` (made at <https://console.groq.com/keys>) and `GEMINI_API_KEY` (made at <https://aistudio.google.com/apikey>). Put them in `.env`, which is git-ignored, or export them in the shell. A key exported in the shell takes the place of one in `.env`, and so does a variable the shell exports empty, which then has its provider skipped. A provider without a key is skipped, with a line that names the variable and where a key is made.
- **What it asks:** whether the provider takes the key, and whether the models Actio means to use are among those it offers that key: Groq's `openai/gpt-oss-120b` and `openai/gpt-oss-20b`, the Gemini API's `gemini-3.6-flash` and `gemini-3.5-flash-lite`. A model of the Gemini API's list that can't be asked a question, such as one that makes embeddings, isn't counted among those offered. Then, for each model, what the provider says of it, and one short question, "Reply with the word OK.", through the provider's OpenAI-compatible API, which Actio's client speaks. Each question counts against your account's limits like any other. Seen with a real key on 2026-11-25, the Gemini API lists models its free tier doesn't include, `gemini-3.1-pro-preview` among them, and refuses a question to one with 429 and a limit of 0, which is why each model is asked something. Nothing is retried.
- **What it prints:** for each model, its window and its longest answer, each where the provider says it, and on the Gemini API whether it can reason. Groq's come from its list of models, whose entries carried both on 2026-11-25. Then how long the model took to answer, and how many tokens the question and the answer were; and each limit the answer's headers state, with what is left and when it is full again. A failure is one line, under the provider or the model it is about: a key that can't be one, with a space, a quote, or a character outside visible ASCII in it, with which nothing is asked; a key refused; a model that isn't offered, with those that are; a question refused, with how long the provider asks to wait when it says; a provider that can't be reached or doesn't answer in time; and an answer that isn't one. The run itself prints no key and no part of one. Of a provider's own text, such as an error's message, the whole key and any piece of it six characters long or longer are hidden before it is printed: a shorter piece that a provider quotes is printed as it is.
- **What the providers don't state:** seen with real keys on 2026-11-25, Groq's answers' headers state requests a day and tokens a minute and nothing else, and its list of models states no limit of the account's, so neither says its limits on requests a minute and tokens a day. The run says so, with where to read all four: <https://console.groq.com/settings/limits>. They are the organisation's, not the key's. The Gemini API's answers carried no header about limits, and a refusal at a limit names the limit and the wait in its body: they are read at <https://aistudio.google.com/rate-limit>. They are the project's, and the daily ones start again at midnight Pacific time. One free account's, read there on 2026-11-25: `gemini-3.6-flash` 5 requests a minute, 250,000 tokens a minute and 20 requests a day, as for `gemini-3.8-flash`; `gemini-3.5-flash-lite` 15 requests a minute, 250,000 tokens a minute and 500 requests a day. Under each model, the run says what the answer it got stated, and for an answer that stated none, where to read them.
- **Other models:** name a provider to check it alone, and models after `=`, separated by commas, to ask those instead of its own: `make preflight args=groq`, or `make preflight args="groq=openai/gpt-oss-20b gemini"`, which asks Groq that model and the Gemini API its own. `make preflight args=--help` says more.
- **Exit status:** the script's is 0 when every provider that had a key passed; 1 when any of them failed, and also when none had a key, since a run that checked nothing is no pass; 2 for arguments it can't read, such as a provider it doesn't know. Through `make`, any of them but 0 ends `make` itself with 2, so `make preflight; echo $?` can't tell them apart: the run's last line says which provider passed and which failed, and a usage error is said above it.
- **Private data:** on the Gemini API's free tier, what is sent may be used to improve Google's products and be read by human reviewers, so nothing private goes through a free key.
- It needs the network and your keys, so it isn't part of `make check`, and CI doesn't run it. Its tests run against a fake of both providers, in `scripts/tests/test_preflight.py`. The script is `scripts/preflight.py`.
- **The model client's own tests of the two:** `packages/llm/tests/test_cloud.py` replays exchanges recorded from both, in `packages/llm/tests/fixtures/groq/` and `gemini/`, with the rest of the tests. `make test-cloud` sends the same requests to the real servers instead, with the keys read as `make preflight` reads them: about fifteen short requests, which count against your accounts' limits, and a provider without a key has its tests skipped. Two of them go to `gemini-3.6-flash`, of which the account above had 20 a day: the Gemini API's other exchanges are `gemini-3.5-flash-lite`'s. `make test-cloud args="-k thoughts"` asks one exchange alone, by its test's name. `ACTIO_RECORD_CLOUD=1 make test-cloud` makes the answers the new recordings, tidied as they are written: no header of a request, and the account's organization, Groq's ids of a request and of a chat completion, and a thought's signature each replaced by a stand-in. Review the difference before you commit it, and record again, alone, an answer that is a model too busy. Five exchanges depend on the account's or the provider's state, such as a limit that was reached or a model too busy: they were written from real answers, and are never asked live ([ADR 0027](adr/0027-cloud-models-through-their-openai-compatible-layers.md)). Not part of `make check` either.

## CI

Every push and pull request runs four jobs:

- **Lint, types, tests and build:** `make check`.
- **Quickstart on Linux:** `make up` and `make smoke` on a clean runner with nothing installed beyond Docker.
- **End-to-end tests in a browser:** `make e2e`. A failed run keeps its report, with a trace of each failed test, for a week.
- **Secret scan:** gitleaks over the full history.

Each push to `main` also publishes this site to GitHub Pages.

## Conventions

- **Commits** follow [Conventional Commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `docs:` and so on.
- **Decisions** that would be hard to reverse get an [ADR](adr/index.md).
- **AI coding agents** follow [`AGENTS.md`](https://github.com/fatihrime/actio/blob/main/AGENTS.md). Among other rules, they never commit or push. See [How AI is used](ai-workflow.md).

## This site

`make docs` serves it at <http://localhost:8001> and reloads pages as you edit them. Pages are Markdown files in `docs/`, and the navigation lives in `zensical.toml`. The build is strict: a broken link or a missing page fails `make build`, and so CI.

The site reads lists more strictly than GitHub does, so a list can look right there and wrong here. In a page, and in a package's README that a page includes:

- **a list starts after an empty line.** Right under a line of text it is no list at all: its items run on as text;
- **what belongs to an item is indented by four spaces a level:** a sub-item, a table, a quote, a second paragraph. With two spaces a sub-item joins the list above it.

A check fails when a page breaks either rule (`scripts/check_docs_lists.py`), and names the line.
